WLED Subsystem

This subsystem lets your robot control an LED matrix or strip in real time — displaying static images, scrolling banners, sprite animations, or GIFs. It communicates over the robot's Ethernet network, so it works reliably during competition without any Wi-Fi.

How It Works (Big Picture)

Here is the flow from robot code to glowing LEDs:

Your Robot Code │ │ calls wled.showBitmap("/home/lvuser/deploy/leds/auto.png") │ ▼ WLEDSubsystem • reads the image file from the RoboRIO's disk • converts each pixel to RGBW color data • 50 times per second, sends UDP packets to the LED controller │ │ UDP packets over Ethernet (DDP protocol, port 4048) │ ▼ QuinLED-Dig-Octa board (running WLED firmware) • receives the pixel data packets • drives the physical LED strip/matrix │ ▼ Your LEDs light up!

UDP packets are short network messages — think of them like postcards. The robot sends roughly 50 per second to keep the LEDs updating smoothly. The DDP protocol is just a simple agreed-upon format for those postcards: "here are the colors for LEDs 0 through 31, etc."

WLED is free, open-source firmware that runs on a wide variety of ESP32-based boards. It handles receiving the DDP packets and physically driving the LEDs. You configure it once through a web browser, and then your robot code takes over at match time.

Choosing an LED Controller Board

This subsystem works with any board running WLED firmware that is reachable over the network. The only hard requirement for an FRC robot is wired Ethernet — Wi-Fi-only boards are not reliable enough inside the metal environment of a competition field.

Many WLED-compatible boards exist. The table below lists some good options. For an FRC robot you typically only need one or two LED output channels (one matrix or strip), so there is no need to reach for an 8-channel board unless your design genuinely calls for it.

Board options

BoardChannelsEthernetNotes
QuinLED-Dig-Uno 2 Yes (requires the -ABE "Antenna Board + Ethernet" variant) Compact, well-documented, good starting point for a single matrix.
QuinLED-Dig-Quad 4 Yes (requires the -ABE variant) Middle ground — room to grow if you add more strips later.
QuinLED-Dig-Octa 8 Yes (built-in on the Brainboard-32-8L) Powerful, but overkill for most FRC robots. Heavier and more expensive than necessary if you only need one or two strips.
Wasatch Pixels Quad 4 Yes (built-in) Pre-assembled with level-shifting; available in 5 V and 12 V versions. Sold on Tindie.
Wasatch Pixels Duo 2 Yes (built-in) Smallest Wasatch option; good fit for a single matrix.
AthomTech Ethernet WLED controller 2–4 Yes (built-in) Includes a logic-level shifter and optional microphone; compact form factor.

A full list of WLED-compatible hardware (including community-designed boards) is maintained at kno.wled.ge/features/ethernet-lan/ and the WLED compatible hardware wiki.

Make sure you get the Ethernet variant Several QuinLED boards are sold in both a Wi-Fi-only version and an Ethernet version (the "-ABE" variant, which stands for Antenna Board + Ethernet). Double-check the product page before ordering — the Wi-Fi-only version looks almost identical but will not work reliably on a robot.

How we power the LEDs

We power the LED strips from an external USB-C PD battery pack rather than from the robot's main 12 V battery. This keeps LED current off the robot's power bus entirely, which avoids any risk of browning out the RoboRIO or other electronics if the LEDs draw a large spike.

The chain looks like this:

USB-C PD battery pack (must support 12 V PD output) │ ▼ USB-C PD to bare-wire pigtail cable ← negotiates 12 V from the battery │ ▼ Buck converter (12 V → 5 V) ← steps voltage down for the LED strip │ ▼ LED strip power input (5 V)

Instead of using a separate trigger board, we recommend using a USB-C PD to bare-wire pigtail cable that negotiates 12 V directly from the battery pack and exposes the output as two open wires. A cable like MECCANIXITY USB C Male Plug Bare Wire Pigtail Cable, 22AWG, 12 V 3 A, Type C Plug to 2 Pin Bare Wire Open End Connector keeps the power path fully COTS and avoids soldering a separate trigger module. In our setup, the cable's bare wires land directly in the buck converter's screw-terminal input, so the upstream path stays as an unmodified COTS cable feeding an unmodified COTS board.

The buck converter steps the 12 V down to a stable 5 V for the LED strip. We use a converter like the 2-pack 12 V/24 V to 5 V 10 A step-down converter — wire its input to the pigtail cable's 12 V output and its output to the LED strip's power input. The example pigtail cable above is rated for 3 A at 12 V (about 36 W), so make sure your total LED load stays within that upstream power budget even if your buck converter is rated for more. The controller board itself draws very little current and is powered separately through its own supply input.

Alternative: direct 5 V power path If your LED load is small enough, a direct 5 V COTS cable from the battery pack to the WLED hardware may be a cleaner option than a 12 V cable plus a buck converter. That removes the intermediate converter from the external-battery power path, which may make the setup simpler to explain at inspection. The tradeoff is available power: for example, a 5 V / 3 A cable only gives you about 15 W upstream.
Why a separate battery instead of the robot's PDP/PDH? Our team powers the WLED hardware from a separate USB-C PD battery pack to keep LED current off the robot's main power bus. That reduces the chance that decorative lighting will affect robot performance, and it also means the LEDs can stay on during a brownout. This setup has passed inspection for us at 2026 events, but teams should confirm that their own wiring and usage comply with the current FRC manual and local inspection guidance.
⚠ Check USB-C PD compatibility Not all battery packs support 12 V PD output. Before buying, confirm that the battery explicitly lists 12 V as a supported PD output voltage in its spec sheet. Basic phone charger banks typically only go up to 9 V or 5 V and will not work.

Setting Up the WLED Board

You only need to do this setup once per board (or when setting up a new robot). You configure WLED through its built-in web interface — open a browser and navigate to the board's IP address.

Step 1 — Get WLED running

Follow the getting-started guide for whichever board you chose. Most pre-assembled boards (QuinLED, Wasatch, AthomTech) come with WLED pre-installed; check your board's product page to confirm. If your board needs firmware flashed, WLED's own flashing instructions are at kno.wled.ge/basics/install-binary/.

Step 2 — Assign a static IP address

Your robot code needs to know where to send the LED data, so the board needs a fixed (static) IP address that never changes. A good convention for FRC is to use your team number in the address: 

10.TE.AM.11

For example, team 9999 would use 10.99.99.11. In the WLED web UI go to Config → Network (for Ethernet) and set the static IP there. Write the address down — you will put it into your robot code as controllerAddress.

Step 3 — Enable the DDP receiver

DDP is the protocol this subsystem uses to send pixel data to WLED. It is turned off by default, so you need to switch it on.

  1. Open the WLED web UI in a browser.
  2. Go to Config → Sync Interfaces.
  3. Find the DDP section and enable the DDP receiver.
  4. Leave the port at the default (4048) unless you have a reason to change it. The subsystem defaults to 4048 as well.

More detail on DDP: kno.wled.ge/interfaces/ddp/

Step 4 — Configure your LED layout

In Config → LED Preferences, tell WLED how many LEDs are connected and how they are wired. The total number of LEDs must equal width × height (the same values you will put in WLEDConfig in Java).

The subsystem sends pixels starting from LED index 0 and moving row by row left to right, so the physical wiring of your strip must follow that same order.

Tip — brightness limiting WLED has a current-limit setting under Config → LED Preferences → Maximum Current that can silently cap the brightness of your LEDs. If your LEDs look dimmer than expected even when showing white, raise this limit (or remove it if your power supply is properly sized and fused).

Adding the Library to Your Robot Project

The WLED library lives in its own folder alongside the Robot project. To use it, you tell Gradle (the build system) where to find it and how to link it. This is called a composite build — Gradle compiles the library from source at the same time as your robot code, so you never have to manually publish or copy JAR files.

Expected folder layout

YourRepo/ ├── Robot/ ← your WPILib robot project └── Subsystems/ └── WLED/ ← this library

If your folder names or relative paths are different, adjust the paths in the steps below accordingly.

Step 1 — Edit settings.gradle in the Robot project

Open Robot/settings.gradle and add the following block anywhere after the pluginManagement { ... } section: 

includeBuild("../Subsystems/WLED") {
    dependencySubstitution {
        substitute(module("frc.kauaibots.subsystems:wled")).using(project(":"))
    }
}

This tells Gradle: "when anyone asks for the library named frc.kauaibots.subsystems:wled, use the local source code at ../Subsystems/WLED instead of looking it up online."

Step 2 — Add the dependency in build.gradle

Open Robot/build.gradle and find the dependencies { } block. Add this line inside it: 

implementation 'frc.kauaibots.subsystems:wled'

Step 3 — Make the JAR task depend on the WLED JAR

Still in Robot/build.gradle, find the jar { } block and add this line inside it: 

dependsOn gradle.includedBuild("WLED").task(":jar")

This ensures the WLED library is compiled and bundled into your robot's JAR file before it gets deployed to the RoboRIO.

How to verify it worked After saving both files, open a terminal in the Robot project folder and run ./gradlew compileJava. If the build succeeds without errors, Gradle found and compiled the WLED library correctly.

Using the Subsystem in Java

Step 1 — Create a WLEDConfig

WLEDConfig is a simple data object that tells the subsystem where your LED controller is and how big your LED matrix is. 

import frc.kauaibots.subsystems.wled.WLEDConfig;

WLEDConfig config = new WLEDConfig(
    "10.99.99.11",  // IP address you assigned to the QuinLED board
    4048,           // DDP port — leave at 4048 unless you changed it in WLED
    32,             // width of your LED matrix in pixels (number of columns)
    16,             // height of your LED matrix in pixels (number of rows)
    8               // rowsPerPacket — leave at 8 unless you have a reason to change it
);
ParameterWhat it means
controllerAddress The static IP address you assigned to the QuinLED board in Step 2 of the WLED setup.
ddpPort The UDP port for DDP communication. The WLED default (and the subsystem default) is 4048. Only change this if you specifically changed it in WLED.
width How many LEDs wide your matrix is (the number of columns).
height How many LEDs tall your matrix is (the number of rows). For a single strip treated as one row, use 1.
rowsPerPacket How many rows of LEDs are packed into each network packet. A value of 8 is a safe starting point for most setups.

Step 2 — Create a WLEDSubsystem

import frc.kauaibots.subsystems.wled.WLEDSubsystem;

WLEDSubsystem wled = new WLEDSubsystem(config);

Create this in RobotContainer like any other subsystem. The subsystem opens a network connection immediately when it is created, so only create one instance.

Step 3 — Call a command method to show something

The subsystem has four methods, each returning a Command that you can schedule or bind to a trigger like any other WPILib command. All four work during disabled mode (before and after a match), so your LEDs will show even in the pits.

MethodWhat it doesImage requirements
showBitmap(path) Displays a single still image on the matrix. PNG, JPG, or BMP. Width and height must each be at least as large as your matrix dimensions. Extra pixels on the right/bottom are ignored.
showBitmapAsMarquee(path) Scrolls an image horizontally, one pixel per frame, wrapping around continuously. Great for scrolling text banners. Same formats. Height ≥ matrix height. Make the image wider than your matrix to get a longer scroll before it repeats.
showFromBitmapAnimationStrip(path) Treats one wide image as a row of animation frames side by side, and plays them in sequence (like a film strip). Same formats. Width must be an exact multiple of your matrix width. Each frame is one matrix-width slice of the image.
showGif(path) Plays an animated GIF at the speed embedded in the file, looping forever. Animated GIF. Every frame must be exactly your matrix width × height — no auto-scaling.
Where do image files live? Put image files in the src/main/deploy/ folder inside the Robot project. GradleRIO automatically copies everything in that folder to /home/lvuser/deploy/ on the RoboRIO when you deploy.

So a file you save at src/main/deploy/leds/auto.png will be available on the robot as "/home/lvuser/deploy/leds/auto.png" — that is the path string you pass to the command methods.
Load commands early, not mid-match When you call showBitmap(...) the subsystem reads the image file from disk right then. Call all of your show*() methods during RobotContainer construction (before the match starts) and store the returned Command objects as fields. This way the disk reads happen at startup, not during autonomous or teleop.

RGBW color notes

The subsystem sends color data in RGBW format (four channels per LED: Red, Green, Blue, White). It automatically converts regular RGB colors from your images into RGBW by pulling out the neutral "white" component from each pixel. You do not need to do anything special — just use normal color images.

If your LED strip is RGB-only (not RGBW), WLED will still accept the data; it blends or ignores the White channel depending on your strip type setting in WLED.

Creating Your Image Files

Here is a visual guide to what each animation mode expects. These examples assume a 32×16 LED matrix.

showBitmap — single still image

Image file (must be at least 32 wide × 16 tall): ┌────────────────────────────────┐ │ │ ← 32 pixels wide, 16 pixels tall │ your artwork here │ (exactly or larger) │ │ └────────────────────────────────┘ The top-left 32×16 region is shown. Extra pixels on the right or bottom are ignored.

showBitmapAsMarquee — scrolling banner

Image file (width can be anything, height ≥ 16): ┌─────────────────────────────────────────────────────────────┐ │ GO TEAM! GO TEAM! GO TEAM! │ └─────────────────────────────────────────────────────────────┘ ↑ wide image scrolls left, one pixel per frame (50 fps) ↑ wraps around — the right edge connects back to the left edge

showFromBitmapAnimationStrip — frame-by-frame animation

Image file (width = 32 × number of frames, height ≥ 16): ┌────────────────┬────────────────┬────────────────┬────────────────┐ │ frame 1 │ frame 2 │ frame 3 │ frame 4 │ │ (32 wide) │ (32 wide) │ (32 wide) │ (32 wide) │ └────────────────┴────────────────┴────────────────┴────────────────┘ ↑ total width = 128 pixels (4 frames × 32) Frames play left to right at 50 fps (20 ms each), then loop.

showGif — animated GIF

Animated GIF (must be exactly 32 wide × 16 tall): ┌────────────────────────────────┐ │ frame 1 of N │ ← each frame plays for the duration └────────────────────────────────┘ set in the GIF file ← frames loop back to the start automatically
⚠ Image errors are silent If an image file is the wrong size, missing, or in an unsupported format, the subsystem will log an error to the Driver Station but the LEDs will just stay at whatever they were showing. Always check the Driver Station log after deploy if your LEDs are not doing what you expect.

Full Examples

Basic setup in RobotContainer

import frc.kauaibots.subsystems.wled.WLEDConfig;
import frc.kauaibots.subsystems.wled.WLEDSubsystem;
import edu.wpi.first.wpilibj2.command.Command;

public class RobotContainer {

    // --- WLED configuration ---
    // Change the IP address to match whatever you assigned to your board.
    // Change width/height to match the size of your actual LED matrix.
    private static final WLEDConfig WLED_CONFIG = new WLEDConfig(
        "10.99.99.11",  // IP address of QuinLED-Dig-Octa
        4048,           // DDP port (leave at 4048 unless you changed it in WLED)
        32,             // LED matrix width in pixels
        16,             // LED matrix height in pixels
        8               // rows per packet (8 is a safe default)
    );

    // Create the subsystem — only do this once!
    private final WLEDSubsystem wled = new WLEDSubsystem(WLED_CONFIG);

    // Load all animations at startup (reading files now avoids delays mid-match)
    private final Command ledsAuto     = wled.showBitmap(
                                             "/home/lvuser/deploy/leds/auto.png");
    private final Command ledsTeleop   = wled.showGif(
                                             "/home/lvuser/deploy/leds/teleop.gif");
    private final Command ledsDisabled = wled.showBitmapAsMarquee(
                                             "/home/lvuser/deploy/leds/banner.png");

    public RobotContainer() {
        configureBindings();

        // Play the scrolling banner animation whenever the robot is disabled
        // (e.g. sitting in the pits, waiting to start).
        wled.setDefaultCommand(ledsDisabled);
    }

    private void configureBindings() {
        // ... your button bindings ...
    }
}

Switching LEDs based on robot state

// In configureBindings() or wherever you set up triggers:

// Light up "ready to shoot" LEDs when the shooter is at speed.
new Trigger(shooter::isAtSpeed)
    .onTrue(wled.showBitmap("/home/lvuser/deploy/leds/shooter_ready.png"))
    .onFalse(ledsTeleop);   // go back to the normal teleop animation

// Play a celebration animation when a button is held.
operatorController.a()
    .whileTrue(wled.showGif("/home/lvuser/deploy/leds/celebration.gif"))
    .onFalse(ledsTeleop);

Matching LEDs to robot mode using AutonomousInit / TeleopInit

// In Robot.java:

@Override
public void autonomousInit() {
    // ledsAuto is a stored Command field in RobotContainer
    robotContainer.getLedsAuto().schedule();
}

@Override
public void teleopInit() {
    robotContainer.getLedsTeleop().schedule();
}

Updating for a New Season

This library is designed to be reused from year to year. Each season gets its own branch (e.g. 2026, 2027) because the library depends on WPILib, which releases a new version each season.

The detailed update procedure is in the file HOW_TO_UPDATE_FOR_THE_CURRENT_YEAR.TXT in the src/main/java/frc/kauaibots/subsystems/wled/ folder. The short version:

  1. Create a new branch for the new season (e.g. branch 2027 from 2026).
  2. Install the new year's WPILib.
  3. Use the WPILib VS Code importer on this project to get updated Gradle files, then copy them back into the branch.
  4. Update the WPILib version numbers in build.gradle and settings.gradle.
  5. Run ./gradlew test from inside the WLED folder to make sure the regression tests pass.
  6. Update the Robot project for the same season and verify it still compiles with the updated WLED library.
